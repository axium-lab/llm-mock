Azure OpenAI API reference

Azure OpenAI · Endpoints

Azure serves the same models as OpenAI through a different front door. Most of the differences are in the routing rather than the payloads — the exception being content filtering, which Azure adds to every response. Two surfaces are served under the /azure/openai prefix.

MethodPathNotes
POST…/deployments/{deployment}/chat/completionsFull chat.completion object, SSE streaming with [DONE], tool calls
POST…/deployments/{deployment}/embeddingsDeterministic unit vectors, correct dimension per model
POST…/deployments/{deployment}/completionsThe legacy endpoint: a text_completion object, n choices per prompt, echo, the filter's verdict attached as on chat
POST/azure/openai/v1/chat/completionsThe newer surface: no api-version, no deployments
POST/azure/openai/v1/embeddingsSame handlers, addressed by model
POST/azure/openai/v1/completionsLegacy completions on the v1 surface
GET/azure/openai/models?api-version=Model catalog, outside the deployment path
GET/azure/openai/deployments?api-version=Deployment listing, one per catalog model
GET…/deployments/{deployment}?api-version=A single deployment, any name
POST/azure/openai/responses?api-version=Responses API, OpenAI's router verbatim: full response object, typed SSE event stream. Not deployment-scoped, as on Azure
GET/azure/openai/responses/{id}?api-version=Stateless: synthesizes a deterministic response for any id
DELETE/azure/openai/responses/{id}?api-version=Idempotent; returns the OpenAI deletion object
POST/azure/openai/responses/{id}/cancel?api-version=Stateless: any id comes back as a cancelled background response
POST/azure/openai/files?api-version=Multipart upload; the file's metadata is carried in its id, so it round-trips without a store
GET/azure/openai/files?api-version=Simulated catalog, filterable by purpose
GET/azure/openai/files/{id}?api-version=404 for the reserved file-missing prefix
GET/azure/openai/files/{id}/content?api-version=Placeholder bytes, or the x-llm-mock-response header
DELETE/azure/openai/files/{id}?api-version=Idempotent
POST/azure/openai/v1/responses, …/{id}, …/{id}/cancelThe same Responses API on the v1 surface, no api-version
POST/azure/openai/v1/files, …/{id}, …/{id}/contentThe same Files API on the v1 surface, no api-version
POST/azure/openai/uploads?api-version=, …/{id}/parts, …/{id}/complete, …/{id}/cancelThe Uploads API, OpenAI's router verbatim; also at /azure/openai/v1/uploads

The classic surface addresses a deployment rather than a model and requires api-version on every call. The v1 surface drops both:

# classic
/azure/openai/deployments/{deployment}/chat/completions?api-version=2024-10-21

# v1
/azure/openai/v1/chat/completions
Azure puts the resource name in the hostname ({resource}.openai.azure.com) and keeps /openai in the path. A mock cannot hand out subdomains, but it does not need to — the SDK takes an arbitrary URL, so the resource simply becomes part of the prefix. Both surfaces run the same handlers, so the same request returns the same body on either.

Azure · Authentication

Azure takes the key in an api-key header rather than a bearer token — the single most common reason an OpenAI-shaped client fails against it. Authorization: Bearer is accepted too, as Entra ID callers use it.

import { AzureOpenAI } from "openai";

const client = new AzureOpenAI({
  baseURL: "http://localhost:3000/azure/openai",
  apiKey: "sk-mock-key-01",
  apiVersion: "2024-10-21",
});

Use baseURL rather than endpoint: the SDK reads OPENAI_BASE_URL from the environment and then refuses to combine it with endpoint, so a stray env var breaks the client before it sends anything. The v1 surface needs no Azure-specific client at all — a plain OpenAI pointed one level deeper at /azure/openai/v1.

The two failures answer differently, and that is Azure's own doing: a missing key is rejected by the API gateway, which knows nothing about the service's error envelope, while an invalid one gets the wrapped shape.

// missing credential — no `error` wrapper at all
{ "statusCode": 401, "message": "Access denied due to missing subscription key…" }

// invalid credential — the service's envelope
{ "error": { "code": "401", "message": "Access denied due to invalid subscription key…" } }

Note that Azure's code is a symbolic string (DeploymentNotFound, BadRequest) where OpenAI uses a snake_case slug or null.

Azure · Deployments

A deployment is a named alias a customer creates in their own Azure resource, pointing at a model. A mock has no resource and therefore no deployments, so any name is accepted — the way every provider here accepts any model id.

What cannot be dropped is the 404. DeploymentNotFound is the error Azure users hit most, and the one their code most needs to handle, so it is driven by the name itself: anything starting with missing- returns the real thing.

{
  "error": {
    "code": "DeploymentNotFound",
    "message": "The API deployment for this resource does not exist. If you created the deployment within the last 5 minutes, please wait a moment and try again."
  }
}

Because a name cannot be looked up anywhere, the listing is served too — one deployment per catalog model, named after the model it points at, so a client configured with deployment: "gpt-4o" works with no further setup. Any other name is described as well, since the mock accepts all of them for inference.

GET /azure/openai/deployments?api-version=2024-10-21

{
  "object": "list",
  "data": [{
    "id": "gpt-4o",
    "model": "gpt-4o",
    "owner": "organization-owner",
    "status": "succeeded",
    "scale_settings": { "scale_type": "standard" },
    "created_at": 1715367049,
    "updated_at": 1715367049,
    "object": "deployment"
  }]
}

That is the legacy data-plane shape — the one that lives under the same prefix as inference. On the real service, managing deployments moved to ARM (management.azure.com), a separate host a mock behind a single base URL cannot represent, so this endpoint exists to let a client discover names without leaving the endpoint it is already pointed at.

The deployment routes the call; the model echoed back is the one the client asked for, since the two need not agree — the SDK only uses model as the deployment segment when no fixed deployment is configured. The reserved prefix belongs to the deployment path only: on the v1 surface there is no deployment to be missing, and missing-one is just a model name.

Azure · Content filtering

The most Azure-specific thing about the service, and the reason an OpenAI-shaped client can meet a response it did not expect. Every chat completion carries the filter's verdict — on the prompt at the top level, on each choice individually.

{
  "choices": [{
    "message": { "content": "Echo: hello" },
    "finish_reason": "stop",
    "content_filter_results": {
      "hate":      { "filtered": false, "severity": "safe" },
      "self_harm": { "filtered": false, "severity": "safe" },
      "sexual":    { "filtered": false, "severity": "safe" },
      "violence":  { "filtered": false, "severity": "safe" }
    }
  }],
  "prompt_filter_results": [{
    "prompt_index": 0,
    "content_filter_results": { /* the four above, plus binary detectors */
      "jailbreak": { "filtered": false, "detected": false } }
  }]
}

To exercise the failure paths, pin the verdict with x-llm-mock-content-filter, as <target> or <target>:<category>:<severity>:

ValueResult
prompt400 with code: "content_filter", and the verdict nested in innererror
completion200 with content: null and finish_reason: "content_filter"
unavailable200, with an error object where the verdict would be — the documented "filter did not run" case

Categories are hate, self_harm, sexual, violence and jailbreak; severities safe, low, medium, high. So completion:violence:high filters the reply and says which category did it.

Two quirks are reproduced deliberately, because code written against OpenAI trips on both. A streamed response opens with a chunk carrying no choices at all, just the prompt's verdict — a client reaching straight for chunk.choices[0] breaks there. And the blocked-prompt error nests its verdict under content_filter_result, singular, against the plural used everywhere else.

None of this provider's shapes could be checked against a live Azure resource. Its routes come from observing what AzureOpenAI puts on the wire, and its payloads from Microsoft's documentation and published examples — but they are not observed responses. The empty first streaming chunk in particular is reconstructed from reported behaviour rather than seen.

Azure · Claude in Microsoft Foundry

Anthropic's Messages API served from an Azure resource. On the real service the path is https://{resource}.services.ai.azure.com/anthropic/v1/*; here the resource becomes the prefix, so the door is /azure/anthropic. The service behind it is Anthropic's own, and so are the payloads, the named SSE events and the error envelope — what Azure changes is the front door.

MethodPathNotes
POST/azure/anthropic/v1/messagesThe Anthropic Messages handler: content blocks, tool_use, thinking, named SSE events ending on message_stop
POST/azure/anthropic/v1/messages/count_tokensSame count as usage.input_tokens on the message
GET/azure/anthropic/v1/models404 — Foundry has no Models API, no Message Batches and no Files, and the Foundry SDK removes them from its client

The Foundry SDK builds its base URL from a resource name; a baseURL stands in for it here. Everything else about the client is the Anthropic SDK:

import AnthropicFoundry from "@anthropic-ai/foundry-sdk";

const client = new AnthropicFoundry({
  baseURL: "http://localhost:3000/azure/anthropic", // in place of `resource`
  apiKey: "sk-mock-key-01",
});

const message = await client.messages.create({
  model: "claude-opus-5", // the deployment name, which defaults to the model id
  max_tokens: 1024,
  messages: [{ role: "user", content: "Hello!" }],
});

The key travels in api-key, Azure's header, or in x-api-key, Anthropic's — the Foundry SDK sends the latter. An Entra ID token goes in Authorization: Bearer and is accepted unvalidated. A rejected credential is answered by Azure's gateway, ahead of the service, so it comes back in Azure's two shapes rather than Anthropic's envelope; everything past the gateway, including the anthropic-version header it still requires, is Anthropic's.

// past the gateway: Anthropic's envelope, with the request id echoed
{ "type": "error",
  "error": { "type": "invalid_request_error", "message": "max_tokens: Field required" },
  "request_id": "req_…" }
Every response carries the two correlation ids Foundry reports: request-id, Anthropic's, which equals the x-request-id the mock stamps everywhere, and apim-request-id, the one Azure API Management assigns on the way through.

Azure · Model Inference API

The Azure AI Model Inference API, the route a Foundry resource exposes for models that are not OpenAI's — Llama, Mistral, DeepSeek, Phi — at https://{resource}.services.ai.azure.com/models/*, here /azure/models. OpenAI's chat completions and embeddings pared down to a common subset, with a flat error envelope and a header deciding the fate of anything outside that subset.

MethodPathNotes
POST/azure/models/chat/completions?api-version=No object, no system_fingerprint; a message of role, content and tool_calls. SSE with [DONE]
POST/azure/models/embeddings?api-version=id, data, usage, model
GET/azure/models/info?api-version=The deployed model, fixed: Phi-4, chat_completion, Microsoft
POST/azure/models/images/embeddings404, in the gateway's shape

model is optional, as on a single-model endpoint, and the response names what ran. api-version is required on every call, exactly as on the classic Azure OpenAI surface. The key travels in api-key, or as a bearer token.

import createClient from "@azure-rest/ai-inference";
import { AzureKeyCredential } from "@azure/core-auth";

const client = createClient("http://localhost:3000/azure/models", new AzureKeyCredential("sk-mock-key-01"), {
  allowInsecureConnection: true, // plain http
});

const res = await client.path("/chat/completions").post({
  body: { messages: [{ role: "user", content: "Hello!" }] },
});

The extra-parameters header decides what happens to a field the API does not specify. With error, the default, the request is refused and the field named; drop and pass-through let it through — there is no model here to pass it to, so the two are the same thing.

// `safe_prompt` is Mistral's, not the API's — 422 unless the header allows it
{
  "status": 422,
  "code": "parameter_not_supported",
  "message": "One of the parameters contain invalid values.",
  "detail": { "loc": ["body", "safe_prompt"], "input": true }
}

// x-llm-mock-content-filter: prompt — the documented content safety failure
{ "status": 400, "code": "content_filter", "message": "The response was filtered", "param": "messages", "type": null }

A credential is checked by the gateway and rejected in Azure's shapes; an unknown path is the gateway's too, a flat { "statusCode": 404, "message": "Resource not found" }. Everything else is the API's own envelope: flat, with the status repeated in the body.

Microsoft now routes Foundry Models through /openai/v1 — served here at /azure/openai/v1 — and has retired the azure-ai-inference SDKs. This door exists for the code written against them. Its shapes come from the SDK's type definitions and the published reference, not from a live resource.
